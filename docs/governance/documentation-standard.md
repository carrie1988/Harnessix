# Harnessix Code 文档工程规范

## 1. 目的

本规范定义Harnessix Code正式设计资料的职责边界、最低结构、追踪方式和生命周期。目标是让未参与实现的工程师仅依据正式文档即可完成以下工作：

1. 理解需求来源、范围和关键取舍；
2. 找到运行时主链、关键状态和持久化事实；
3. 从设计定位到实际源码符号及验证用例；
4. 推演取消、超时、崩溃、重试、恢复和安全拒绝路径；
5. 判断文档描述对应的代码版本以及资料是否仍然有效。

## 2. 基本原则

1. **实现一致**：现行文档描述已合入实现；目标能力必须明确标注为规划，不得与当前能力混写。
2. **单一事实源**：同一事实只在一种文档中完整定义，其他文档链接引用，不复制形成多个版本。
3. **设计先行**：重大变更先形成可评审设计，再实施代码；实现完成后按实际代码回写。
4. **失败优先**：取消、超时、恢复、安全边界和兼容迁移与正常流程具有同等地位。
5. **可追溯**：关键结论必须能追踪到决策、源码符号、测试用例或验证证据。
6. **图文对应**：每张图必须有完整文字说明；图不能替代状态、边界和失败语义。
7. **外部可读**：资料使用简体中文，术语、协议名、类名、函数名和命令保留原文；不得记录临时讨论过程、凭据或个人环境信息。
8. **最少充分**：小修复更新最近的现行模块文档，不为一次性局部修改制造冗余文档。

## 3. 文档分类与单一事实源

| 文档类型 `doc_type` | 核心问题 | 是否随实现更新 | 主要目录 |
|---|---|---|---|
| `product-charter` | 产品解决什么问题、用户和边界是什么 | 是 | `docs/` |
| `roadmap` | 能力按什么顺序交付、何时算完成 | 是 | `docs/roadmap.md` |
| `system-architecture` | 系统上下文、分层、跨模块主链和部署边界 | 是 | `docs/architecture.md`及后续架构目录 |
| `module-design` | 一个模块当前如何实现 | 是 | `docs/modules/` |
| `change-design` | 一次重大变更从旧状态到新状态的增量 | 否；完成后冻结 | `docs/changes/` |
| `contract` | 稳定外部/内部契约、字段与兼容规则 | 是 | `docs/contracts/`或现有契约文档 |
| `adr` | 为什么选择某项长期决策 | 否；只追加结果或被取代关系 | `docs/adr/` |
| `source-research` | 参考项目的可核验证据与独立结论 | 固定参考版本后冻结 | `docs/research/` |
| `test-and-eval-design` | 测试分层、数据集、指标和通过阈值 | 是 | `docs/`及后续测试目录 |
| `validation-evidence` | 一次受控验证的输入、环境和结果 | 否；生成后冻结 | `docs/validation/` |
| `deployment-design` | 安装、配置、升级、回滚和运维 | 是 | `docs/`及后续运维目录 |
| `threat-model` | 资产、信任边界、攻击面和缓解措施 | 是 | `docs/threat-model.md` |
| `governance` | 文档或工程治理规则 | 是 | `docs/governance/` |
| `governance-index` | 同类正式资料的统一导航、状态和阅读顺序 | 是 | 各治理目录的`README.md` |
| `documentation-standard` | 文档工程分类、元数据、评审和门禁规范 | 是 | `docs/governance/documentation-standard.md` |
| `source-reading-guide` | 当前仓库源码主链和推荐阅读路径 | 是 | `docs/guides/` |
| `template` | 新文档的结构和必填内容约束 | 是 | `docs/governance/templates/` |

职责分离规则：

- ADR只解释**决策原因、替代方案和后果**，不得承担完整现行实现说明；
- 模块设计是模块当前行为的事实源，必须在代码变更后同步；
- 重大变更设计描述变更前后差异，完成后保留为历史，不复制整份模块说明；
- 源码研究记录外部证据，Harnessix最终选择必须进入ADR或正式设计；
- 验证证据记录结果，测试规范定义方法和门槛，二者不得混用；
- 路线图只维护交付边界和状态，不堆叠模块内部实现细节。

## 4. 元数据规范

### 4.1 必填YAML头

DOC-1之后新增或重写的正式文档必须以如下元数据开头：

```yaml
---
doc_type: module-design
status: current
version: 1
code_revision: 0123456789abcdef0123456789abcdef01234567
owners:
  - core
modules:
  - agent
related_adrs:
  - docs/adr/0007-agent-loop-and-cancellation.md
related_tests:
  - tests/agent/test_runtime.py
supersedes: []
---
```

字段定义：

| 字段 | 约束 |
|---|---|
| `doc_type` | 使用第3节登记的稳定类型；模板可使用`template` |
| `status` | 只能使用第4.2节枚举 |
| `version` | 文档结构或结论发生实质变化时递增正整数 |
| `code_revision` | 40位Git提交；设计尚未实现时使用`pending`，合入前必须替换 |
| `owners` | 负责维护的团队或角色列表，不写个人对话信息 |
| `modules` | 受影响的源码包或跨模块域；无对应源码时使用`documentation`等明确域名 |
| `related_adrs` | 仓库根目录相对路径列表；没有则为空列表 |
| `related_tests` | 仓库根目录相对路径列表；没有则为空列表并在正文说明验证方式 |
| `supersedes` | 被本文取代的文档路径；没有则为空列表 |

### 4.2 状态枚举

| 状态 | 含义 | 允许作为现行依据 |
|---|---|---|
| `draft` | 尚未完成评审 | 否 |
| `reviewing` | 正在评审，仍可能变化 | 否 |
| `current` | 与标注代码版本一致的当前事实 | 是 |
| `historical` | 历史记录，不再描述当前实现 | 否 |
| `superseded` | 已被其他文档明确取代 | 否 |
| `deprecated` | 仍保留兼容背景但不应继续采用 | 否 |

禁止使用“基本完成”“当前通过”“部分已完成”等自由文本替代机器状态。阶段进度应在正文单独说明。

## 5. 重大变更判定

满足任一语义条件即属于重大变更：

1. 修改公共API、Schema、协议、持久化格式、错误码或兼容承诺；
2. 修改领域状态机、事件顺序、事务边界、迁移策略或事实归属；
3. 修改取消、超时、重试、幂等、对账、崩溃恢复或`UNKNOWN`语义；
4. 修改审批、Sandbox、网络、Secret、权限或扩展供应链边界；
5. 新增服务、中间件、持久化后端、运行模式、平台端口或部署拓扑；
6. 跨越两个及以上顶层生产源码包并改变其职责或调用方向；
7. 关闭一个路线图纵向切片或改变其验收标准。

若语义条件均不满足，但预计生产代码改动超过300行或10个文件，也按重大变更处理并由评审确认是否降级。纯格式化、机械重命名和测试数据更新不能仅因行数触发，但必须证明行为不变。

## 6. 重大变更文档工作流

```mermaid
flowchart LR
    A[需求与源码研究] --> B[重大变更设计草案]
    B --> C[ADR与领域契约评审]
    C --> D[最小正式实现]
    D --> E[正常与失败恢复测试]
    E --> F[真实场景验证]
    F --> G[按实际源码同步模块设计]
    G --> H[文档与代码门禁]
    H --> I[路线图关闭]
```

执行规则：

1. 设计草案在实现前明确背景、目标、非目标、边界、关键数据和失败语义；
2. 长期或跨模块取舍形成ADR，局部实现选择保留在变更设计；
3. 实现和测试必须引用变更设计，评审检查实际代码是否偏离；
4. 偏离设计时先更新设计并重新评审，不允许让文档保留已失效方案；
5. 完成前更新现行模块设计、源码映射、测试映射和兼容说明；
6. 重大变更设计转为`historical`，模块设计保持`current`；
7. 门禁未通过或资料未同步时，路线图切片不得标记完成。

## 7. 设计文档最低结构

### 7.1 通用必备章节

所有`system-architecture`、`module-design`和`change-design`至少包含：

1. 文档摘要与当前/目标能力边界；
2. 需求背景；
3. 设计目标与非目标；
4. 约束、假设和关键术语；
5. 总体架构或模块上下文；
6. 模块职责、依赖方向和禁止边界；
7. 正常流程、失败流程和恢复流程；
8. 领域状态、接口、数据结构和重点字段；
9. 持久化、事务、并发、幂等与兼容迁移；
10. 取消、超时、错误分类和未知结果处理；
11. 安全与隐私边界；
12. 可观测性；
13. 测试设计和验收标准；
14. 源码、测试、ADR及证据映射；
15. 核心业务逻辑伪代码；
16. 已知限制、风险和后续工作。

不适用的章节仍应保留并解释原因，不能直接省略。

### 7.2 按文档类型的图示要求

| 文档类型 | 必备图 | 条件性图 |
|---|---|---|
| 系统架构 | 系统上下文图、容器/组件图、跨模块主流程时序图 | 部署图、数据流图、信任边界图 |
| 模块设计 | 模块上下文/组件图、正常时序图、失败或恢复时序图 | 状态图、类图、数据流图、ER图 |
| 重大变更设计 | 变更前后对比、正常时序图、失败时序图 | 迁移数据流、状态图 |
| ADR | 无强制图，保持决策简洁 | 当图能解释不可逆边界时添加 |
| 源码研究 | 调用链或阅读路线图 | 状态图、对比图 |

涉及持久状态时必须给出状态图或明确的状态转换表；涉及跨进程/网络交互时必须给出时序图；涉及数据持久化、Secret或用户内容流动时必须给出数据流图。

## 8. 图示规范

1. 使用GitHub原生支持的Mermaid：`flowchart`、`sequenceDiagram`、`stateDiagram-v2`、`classDiagram`和`erDiagram`；
2. 节点名称使用领域术语，代码标识符放在反引号或文字说明中；
3. 正常与失败路径不能只靠颜色区分，应使用边标签、线型或独立分支；
4. 图中每个跨模块箭头必须在正文解释调用方向、同步/异步性质和失败返回；
5. 图后必须有“图示说明”和“源码映射”，说明图中的组件对应哪些包、类或函数；
6. 超过20个节点的图应拆分为上下文图和局部图，避免不可读的全景图；
7. 图展示设计结构，真实接口字段、状态值和错误码仍以表格或契约为准。

## 9. 源码与测试链接规范

### 9.1 现行文档

- 使用相对Markdown链接指向仓库中的实际文件，并在同一行给出完整符号名；
- 链接目标以文件为主，目录链接只用于包级索引；
- 不单独依赖易漂移的行号；需要行号时同时写稳定符号名；
- 测试链接必须给出测试文件和测试函数/合同套件名称；
- 源码映射表至少包含“设计元素、源码、关键符号、验证测试、说明”。

示例：

| 设计元素 | 源码 | 关键符号 | 测试 | 说明 |
|---|---|---|---|---|
| 示例状态机 | `src/harnessix/example.py`的相对链接 | `ExampleReducer.apply` | `tests/example/test_reducer.py::test_apply`的相对链接 | 文档中必须替换为真实可点击链接 |

### 9.2 历史文档

重大变更设计和验证证据冻结后，关键源码引用应使用包含40位提交号和行范围的GitHub永久链接，避免后续重构改变历史含义。ADR优先链接现行模块设计；只有必须证明当时实现时才加入永久链接。

### 9.3 链接有效性

- 相对路径、大小写和目标文件必须存在；
- 禁止把本机绝对路径、临时工作树、私有服务器或凭据写入文档；
- 外部研究链接应记录访问日期、参考版本/提交和许可证边界；
- 锚点变更视为兼容性变化，重命名标题时同步所有引用。

## 10. 类、接口和数据设计规范

### 10.1 类与组件

重点类表必须说明：职责、生命周期、拥有的状态、线程/进程安全要求、直接依赖、禁止依赖及扩展点。只罗列类名不构成设计。

### 10.2 接口

每个公共端口、协议方法或事件至少定义：

- 调用者与实现者；
- 输入、输出和版本；
- 前置条件与后置条件；
- 错误类别、重试建议和取消行为；
- 幂等键、超时、并发和顺序约束；
- 安全权限及敏感字段处理；
- 兼容策略和对应合同测试。

### 10.3 数据结构和字段

字段表至少包含：名称、类型、必填性、来源、含义、默认值、约束、敏感级别、持久化位置、兼容规则。状态字段必须列出所有合法值和转换发起者；标识字段必须说明作用域与唯一性；时间字段必须说明时区和单调/墙钟语义。

## 11. 伪代码规范

伪代码用于解释跨函数业务规则，不复制实现语言语法。必须体现：

1. 前置校验和权限判断；
2. 持久事实写入顺序；
3. 副作用发生点；
4. 取消、超时和异常分支；
5. 重试、幂等、对账或`UNKNOWN`处理；
6. 事务提交和对外事件发布顺序。

伪代码中的每个关键步骤都应能在源码映射表中找到实现符号。

## 12. 评审清单

### 12.1 设计评审

- [ ] 背景、目标、非目标和约束可验证；
- [ ] 当前能力与规划能力明确分离；
- [ ] 模块职责和依赖方向没有循环或隐式旁路；
- [ ] 正常、取消、超时、失败、恢复和安全拒绝路径完整；
- [ ] 状态、接口、数据和重点字段具有正式契约；
- [ ] 持久化、并发、事务、幂等和迁移边界清楚；
- [ ] 图、文字、伪代码和源码映射相互一致；
- [ ] 替代方案及取舍已记录，长期决策进入ADR；
- [ ] 测试可以独立证明验收标准。

### 12.2 合入检查

- [ ] `code_revision`对应实际实现提交或按合入流程更新；
- [ ] 所有相对链接、源码文件和测试目标存在；
- [ ] 新增/修改公共契约具有合同测试；
- [ ] 模块设计已按最终源码同步；
- [ ] 失败恢复、安全和兼容测试通过；
- [ ] 路线图和README只声明已验证能力；
- [ ] 文档不包含凭据、本机绝对路径或临时讨论过程；
- [ ] 变更设计、ADR和验证证据的状态正确。

## 13. 命名、版本与目录

- 文件名使用小写kebab-case；ADR继续使用四位编号前缀；
- 模块设计目标路径为`docs/modules/<package>.md`；
- 重大变更设计目标路径为`docs/changes/<版本>-<主题>.md`；
- 文档标题使用正式产品名和明确主题，不使用“临时”“最终版2”等名称；
- 破坏文档契约或大幅重组章节时递增`version`；文字修正可不递增；
- 被取代文档保留仓库历史，并设置`superseded`和`supersedes`关系，不静默删除决策证据。

## 14. 存量迁移策略

DOC-1.0之前的133份文档作为存量基线保留，不因缺少新元数据或章节立即判定CI失败。迁移遵循：

1. DOC-1.1先建立导航和系统级事实源；
2. DOC-1.2用Agent Runtime和Action Plane形成黄金样例；
3. DOC-1.3、DOC-1.4按运行主链逐包补齐现行模块设计；
4. DOC-1.5拆分聚合文档并标记历史资料；
5. DOC-1.6已将全部迁移后Markdown和新增重大变更纳入严格门禁。

不得通过机械增加空章节、无意义图或重复源码来提高合规数字。迁移完成度以他人能否据文档定位、实现、测试和维护为准。

DOC-1.5结束时，仓库内189份Markdown均已完成标准YAML元数据和生命周期迁移；该数字包含DOC-1期间新增的现行模块设计、运维资料、历史索引以及ADR/研究索引，不改写DOC-1.0的133份起始基线。加入ADR 0077和DOC-1.6详细设计后，DOC-1.6关闭时的191份Markdown全部执行严格门禁；后续新增或修改文档直接适用本规范，不再使用“存量暂不阻断”豁免。
