# ADR 0044：Coding Eval任务、证据与确定性评分基线

- 状态：已接受并实现0.5.5a
- 日期：2026-09-06
- 范围：任务/最终回答/报告契约、Git实况采集、Session证据评分和报告原子写入

## 1. 背景与目标

0.5.4c已经把失败测试、受管Patch、再次测试、Git状态/差异和最终回答接成一个确定性闭环，但夹具由脚本Provider逐步驱动。它能证明Runtime组合正确，不能证明模型能在真实仓库自主定位缺陷，也不能形成可跨提交比较的质量基线。

0.5.5需要同时避免两种错误：一是只检查模型是否生成某个Golden Patch，从而拒绝其他正确实现；二是只看最终测试通过，忽略任务基线不可复现、越界修改、测试/差异未核对和最终回答失真。为控制变更面，本ADR只实现0.5.5a的评测契约与评分层，不在同一片引入数据集物化、真实模型调用或源目录合入。

## 2. 架构与模块边界

```text
CodingEvalTask v1
        │
        ▼
受信Eval编排器（0.5.5b） ──► AgentRuntime / Action Worker / Managed Patch
        │                                │
        │                                └─► 持久Session事实
        ├─► 基线/最终隐藏检查摘要
        └─► 固定Git只读端口 ──► EvalGitEvidence
                                         │
                                         ▼
                              coding-eval-grader/v1
                                         │
                                         ▼
                              CodingEvalReport v1
```

新增`harnessix.evals`，职责严格分离：

- `contracts.py`：冻结任务、检查观察、Git证据、结构化最终回答、环境和报告Schema；
- `git_evidence.py`：复用0.5.4c的`GitReadRuntime`采集HEAD、变更类型、暂存区和完整观察摘要；不增加Git命令面；
- `grader.py`：只读取已完成Turn、受信检查摘要和Git证据，不执行模型、测试、Patch或Git写操作；
- `report.py`：最多1 MiB的JSON报告原子读写，不负责上传、聚合或访问控制。

Eval编排器是受信边界。它必须从原Session Store取得经Reducer重放的Turn，并从后续数据集运行器取得真实检查摘要；模型不能提交或修改这些证据。0.5.5a的公共函数本身不是防恶意宿主的远程证明系统。

## 3. 版本化任务契约

`harnessix.coding-eval/v1`固定：

- 稳定`task_id`与单调任务版本；
- 仓库名称、无凭据来源、40—64位来源revision和缺陷基线树SHA-256；
- 用户Prompt、允许修改的已有相对路径和最大文件数；
- 模型可选择的必跑测试Profile；
- 基线必须失败且最终必须通过的行为检查；
- 基线不得失败、最终必须继续通过的回归检查；
- 原Agent `Budget`和`coding-eval-grader/v1`版本。

路径必须是唯一有序的受限POSIX相对路径。行为检查与基线缺陷检查集合必须相等，且不能与回归检查重叠。预算拒绝字符串到数字等类型强转。任务指纹由完整规范JSON计算；Prompt、预算、路径或评分器版本变化都会得到不同指纹。

本契约不保存测试命令、隐藏检查路径或凭据。测试命令仍由宿主Profile和后续隐藏检查运行器持有，不能从模型输出或任务Prompt解析。

## 4. 评分语义

评分不比较唯一补丁文本，而要求以下14项固定检查全部成立：

1. 运行使用的缺陷基线树与任务一致；
2. 每个行为检查在基线阶段唯一存在且失败；
3. 最终检查集合无缺失、重复或额外项；
4. Agent Turn正常完成；
5. 行为检查最终全部通过；
6. 回归检查最终全部通过；
7. HEAD仍是缺陷基线提交；
8. 变更非空，且只涉及允许的已有普通文件；
9. 修改文件数没有超过任务上限；
10. 暂存区保持干净；
11. Session中每个必跑Profile都能证明“失败结果→已归因Patch→通过结果”的顺序；
12. 通过测试之后又成功读取`git_status`和`git_diff`；
13. 最终回答严格符合JSON协议，声明路径等于真实Git路径，声明的必跑测试均通过；
14. 模型步骤和Token没有超过任务预算。

最终回答协议为：

```json
{
  "summary": "修复说明",
  "changed_paths": ["src/package/module.py"],
  "tests": [{"profile": "unit", "passed": true}]
}
```

协议要求模型正文就是JSON对象，不接受Markdown围栏或自然语言猜测。`summary`只用于本次内存解析，持久报告仅保存整份回答SHA-256、UTF-8字节数和已解析声明，不保存模型语义摘要。

## 5. 结果与失败分类

报告结论分为：

- `passed`：全部检查通过；
- `failed`：任务可复现，但Agent在Runtime、正确性、回归、修改边界、回答或预算方面失败；
- `invalid`：仓库树不匹配、缺陷基线意外通过，或最终检查集合不是任务定义，不能把该次运行计入模型成功率。

失败可同时归入`runtime`、`correctness`、`regression`、`forbidden_edit`、`final_answer`、`budget`和`eval_infrastructure`。报告校验器强制固定检查集合、唯一有序失败分类以及`invalid`与基础设施失败的一致性，避免手工删掉失败项后仍构造`passed`报告。

报告只包含任务指纹、Provider/Model标识、平台/隔离摘要、检查结论、检查输出摘要、Git路径/摘要和计数，不包含Diff、测试日志、Prompt、模型summary、API Key或Session正文。路径和Provider标识仍可能属于内部元数据，部署层必须控制报告读取权限；本设计不承诺通用DLP。

## 6. Git、错误与安全边界

`collect_git_evidence`继续使用固定Git可执行文件和0.5.4c已验证的禁用配置。状态超过200项、不是精确仓库根、没有HEAD、Git超时或证据类型错误均拒绝评分，不截取一部分路径后继续。工作区Diff正文最多48 KiB公开前缀，但报告只保存Git对完整已观察输出计算的SHA-256和字节数。

报告写入要求宿主预先创建输出目录；临时文件使用0600权限，完整写入并`fsync`后在同目录`replace`，再同步目录。目标符号链接被拒绝，父目录缺失等I/O错误统一映射为公开写入失败；读取使用`O_NOFOLLOW`、普通文件类型和1 MiB上限。写入失败不会改变Eval结论事实，但编排器必须把报告持久化失败当作运行发布失败，而不是静默丢失。

本片不执行不可信仓库代码，因此没有新增Sandbox声明。0.5.5b运行真实任务时仍只能在私有受管副本中执行宿主固定检查；在0.7隔离后端完成前，不能把它作为任意第三方仓库的生产执行边界。

## 7. 取舍

### 不使用Golden Patch

同一行为可以有多种正确实现。唯一补丁只适合检测数据集是否被泄漏，不适合作为主评分标准。v1以隐藏行为、回归、禁止修改和真实Git证据评分。

### 不使用LLM Judge

LLM Judge会引入模型方差、额外费用和Prompt注入面。v1要求结构化最终回答，并与机器事实精确比对；代码质量的更复杂评分留待有可复现实验后增加新评分器版本。

### 不把单次真实模型结果当能力基线

0.5.5c必须记录相同任务的多次试验，分别报告Runtime错误和Provider方差。0.5.5a只证明评分基础设施可用，不提供模型成功率。

### 不在评分器中实现源目录交付

评分工作区保持未提交Diff，便于核对和销毁。变更包、来源漂移复核、冲突和显式合入属于0.5.5d，不能由`passed`报告隐式授权。

## 8. 兼容、部署与验收

本片新增三份v1 Schema，不修改Agent v9、Session migration11、Action/Process/Artifact/Patch协议，不增加数据库迁移、依赖、网络调用或中间件。

自动测试覆盖严格字段/路径/预算/来源凭据、任务指纹、成功评分、不可复现基线、额外隐藏检查、反馈顺序、越界修改、回答不一致、真实Git rename/staged/untracked分类、报告0600原子往返、缺失父目录错误映射及符号链接/损坏拒绝。Linux运行全量测试，macOS工具作业显式纳入`tests/evals`。0.5.5b完成前，项目仍不能宣称已在非示例仓库完成真实缺陷自主修复。
