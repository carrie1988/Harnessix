# ADR 0021：并发 Session 初始化的 WAL 切换边界

- 日期：2026-09-03
- 状态：采纳，0.4 收口硬化

## 1. 问题与求证

百炼兼容修复后的完整回归中，既有双连接初始化测试暴露 `storage_busy`；30 轮两连接真实 SQLite 复现出现 6 次失败，发生位置均为迁移提交后的 `PRAGMA journal_mode = WAL`，不是迁移校验和错误。

[SQLite WAL 锁说明](https://www.sqlite.org/walformat.html)说明进入 WAL 需要排他锁；[busy handler 文档](https://www.sqlite.org/c3ref/busy_handler.html)说明为避免锁升级死锁，SQLite 可能不调用等待处理器。因此原来的 `busy_timeout=5000` 并不保证模式切换一定等待其他初始化连接完成。

## 2. 决策

1. 保持原迁移事务、应用身份、校验和、完整性检查与提交顺序不变；迁移完成后先关闭连接，释放所有游标与锁。
2. 使用新的短生命周期连接切换 WAL，不复用仍可能持有读锁的迁移连接。
3. 仅对 WAL 切换的 `SQLITE_BUSY` 做协作式等待与重试，等待窗口 5 秒，间隔最多 50 毫秒。这个专用连接设置 `busy_timeout=0`，避免每次尝试又叠加驱动的阻塞等待。
4. 不重跑 Migration，不重放模型/工具/Action，不引入通用数据库自动重试。其他错误立即走现有固定错误分类；窗口耗尽保留 `storage_busy`。
5. 显式读取并验证返回模式为 `wal`；游标和连接均关闭。Task 取消直接传播并清理资源，不继续重试。
6. 数据库已完成迁移但 WAL 尚未启用时，初始化失败仍如实返回；后续显式初始化可继续。不会因忙锁回滚已提交的迁移或伪报成功。

窗口只约束 WAL 忙锁的重试等待，不是整个初始化过程或文件系统 I/O 的硬超时。外部长期持锁依然可能导致 `storage_busy`，由宿主按原请求规则处理。

## 3. 验收

- 对实际旧提交 `9f24961` 注入两次 WAL 忙锁，原实现确定性失败；新实现仅重试 WAL，Migration 只执行一次。
- 新增 8 项测试：20 轮四连接首次初始化、短暂忙锁、窗口耗尽与后续初始化、两类非忙锁错误、等待取消/连接关闭、真实 SQLite 写锁竞争、模式未实际生效。
- 真实竞争用例等待捕获到 SQLite 错误后才释放锁，不依赖任意睡眠碰巧制造竞态。
- 既有未知版本/外部数据库拒绝、Migration 哈希、混合历史升级、故障恢复与完整回归全部保留。

## 4. 非目标

不部署数据库服务、不扩大 Session 多宿主所有权、不改变 Snapshot/Event 事务，不更改 Schema 或历史 SQL 文件。本修复解决 SQLite 启动阶段的已复现竞争，不宣称任意文件系统或无限并发都不会忙锁。
