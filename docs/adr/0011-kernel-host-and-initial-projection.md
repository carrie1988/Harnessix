# ADR 0011：0.3 Kernel 使用进程内宿主与初始聚合投影

- 状态：已接受
- 日期：2026-09-03
- 范围：0.3.1 实施切片

## 背景

0.2 已确定 Agent 协议使用 JSON-RPC 2.0，但完整 App Server 在 0.8 实现。0.3 必须先验证 Runtime 状态与故障语义，不应为测试内核提前开发一套客户端协议。

此外，事件日志需要查询快照，但当前没有长会话的访问基准，不能同时实现完整分页数据库与 Agent Loop。

## 决策

1. 0.3.1 提供 async context manager 形式的进程内 AgentRuntime；
2. ModelProvider、ToolRuntime 和 SessionStore 都通过类型端口注入；
3. 本地 SQLite 数据库同一时刻只允许一个 Runtime 宿主，使用 OS advisory lock；
4. SQLite 事件提交仍使用事务和 sequence CAS，不靠内存锁实现跨连接正确性；
5. 首批投影为 Thread 聚合快照；事件结构与 Reducer 独立，后续增加规范化查询投影而不改变既有事件事实；
6. 先开放无审批的只读 Tool 端口，写操作和审批工具返回未开放错误；
7. 0.3.1 的 Provider Contract 实现归一化文本和完整 Tool Call 子集，原始参数流解析留给 0.4；
8. 0.3.1 完成不等于 0.3 里程碑完成。

## 结果

### 收益

- 不依赖外部模型、中间件或 UI 就能验证完整持久闭环；
- 保留既有 Action Plane，不增加跨语言或框架依赖；
- 进程被强制终止后，第二宿主只能在 OS 释放锁后接管；
- 完整事件支持之后重建新查询投影。

### 限制

- 仅面向本地 macOS/Linux 单宿主，不是分布式 Session；
- 完整聚合快照有历史增长成本，不能作为长会话最终方案；
- 当前取消依赖可信 Provider/Tool 的协作，硬进程终止属于后续 Process Runtime；
- 不提供真实写工具或审批界面；
- UUIDv7 不提供同毫秒内严格单调性，数据库 sequence 才是事件顺序。

## 后续门槛

- App Server 只能调用同一 Runtime 端口，不重新实现 Loop；
- 0.6 长会话前完成分页/规范化投影和体积基准；
- 0.7 安全执行前不得宣称只读元数据等于 OS 隔离；
- 持久审批、完整错误/Item 和可观测性仍属于 0.3 剩余验收。

## 被否决方案

### 先实现完整 App Server 再测试 Kernel

增加了协议、连接、审批 UI 和背压变量，推迟核心恢复语义验证。

### 只用进程内锁保护会话

无法阻止第二进程把正在执行的 Turn 当成崩溃状态恢复。

### 立即实现全部查询表和分页

缺少真实历史访问模式，容易把数据库优化与领域模型正确性混在一个迭代。
