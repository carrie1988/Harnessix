# ADR 0126 会话历史的增量校验

- 状态：评审中
- 日期：2026-11-10

## 背景

认证Session的每个事件带一个MAC签名（Seal），所有Seal按序串成一条无密钥哈希链；Thread另有一个
签名的检查点，记录事件数、链尾哈希和历史总字节。按游标读取事件（`events(after=k)`）时，
`authenticated_events`每次都从第1个事件开始重验全部MAC、重算整条链，再返回第k个之后的事件，
且整个过程必须在10秒内完成。

问题：

1. 单次读取的代价随历史长度线性增长，按页重放完整历史是平方级。945个事件的终态证据重放需要16.6秒，
   离Harbor运行器30秒的重放期限不远；
2. 任务命令占满容器CPU时，长会话的普通读取会超过10秒期限（`publication_history_timeout`），
   评测侧只能用重试绕开（6fc8ae67）；产品里恢复长会话同样变慢。

## 决策

进程内缓存已验证的链前缀，游标读取只校验本次返回的事件（用户2026-11-10批准，选项A）。

1. **缓存。** `VerifiedPrefixCache`属于`SQLiteSessionStore`实例，只在内存中，从不落盘：按Thread保存
   “第i个事件之后的链哈希与累计字节”。缓存绑定写入它时的Publication Binding，Binding变化即清空；
   最多缓存若干Thread，超出时淘汰最久未用的。
2. **游标读取（after>0）。** 缓存有第k个前缀时，只读取序号大于k的事件：逐个验证MAC与身份，
   从缓存的第k个前缀继续串链并累计字节，最后与签名检查点比对事件数、链尾哈希和总字节。
   一致才返回，并把新前缀写入缓存。
3. **回退。** 缓存没有第k个前缀，或增量校验不成立时，丢弃该Thread的缓存，按原方式从根全量校验；
   全量校验成功后重建缓存，失败按原错误返回。
4. **仍然全量校验。** 从头读取（after=0）、整段历史读取（恢复会话、重放进Reducer、Fork来源校验）
   不走缓存，行为不变。10秒期限与资源上限不变。

## 安全边界

- **交付的数据仍然全部可信。** 本次返回的每个事件都验过MAC，它们的顺序与完整性由“缓存前缀+本次事件”
  重算的链与签名检查点相等来约束；检查点本身有签名，攻击者不能伪造。
- **减弱之处。** 同一进程内，已经验证过、本次不返回的较早事件，在游标读取时不再重验。若有人在
  进程运行期间直接改写数据库里这些旧记录，不会在游标读取时发现，而要到下一次全量读取（进程启动、
  恢复会话、Fork）才发现。由于这些记录本次不交付，被改写的内容不会经游标读取到达调用方。
- **威胁模型。** 能改写用户本地Session数据库的攻击者已经拥有该用户账户权限；本设计不改变对这类
  攻击者的最终检测（全量读取仍会发现），只把检测从每次游标读取推迟到下一次全量读取。
- 缓存不跨进程、不跨Binding、不落盘，进程退出即失效，不产生需要保护的新持久状态。

## 后果

- 按页重放从平方级降为线性；长会话的增量读取只与新事件数量成正比。
- 评测侧的读取重试（6fc8ae67）保留为第二道防线，不再是长会话的主要保障。
- 新增约百行代码与一个模块；`authenticated_events`的校验循环抽成全量与增量共用的函数。
