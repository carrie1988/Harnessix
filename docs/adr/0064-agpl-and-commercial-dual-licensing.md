# ADR 0064：AGPL社区版与商业许可证双许可

- 状态：已接受
- 日期：2026-09-08

## 背景

Harnessix Code已经公开发布到GitHub，仓库原许可证为MIT。MIT允许任何获得副本的人使用、复制、修改、分发、再许可和销售软件，只要求保留版权与许可证声明；它适合最大化采用，但不能约束闭源衍生发行版或闭源托管服务。

项目仍需要公开源码、接受社区验证并保留商业化空间，因此不采用附加“禁止商业使用”条款的自定义许可证，也不把Source Available误称为开源。

## 决策

1. 从首次同时提交本ADR和新`LICENSE`的版本开始，Harnessix Code社区版采用`AGPL-3.0-only`。
2. 此前已经在MIT下发布的提交和副本继续适用其取得时的MIT许可证；后续许可证变更不改变既有版本已经授予的许可。
3. 版权所有者为`Zhang Jinhui`。仓库通过`COPYRIGHT.md`记录权利主体与历史边界。
4. AGPL社区版允许商业使用，但分发衍生版本或通过网络向用户提供修改版本时，必须履行AGPL对应源码等义务。
5. 需要闭源嵌入、闭源修改或不按AGPL发布对应源码的主体，可以向版权所有者申请独立商业许可证。`COMMERCIAL_LICENSE.md`只说明授权渠道和适用场景，本身不授予商业许可。
6. AGPL代码许可证不授予Harnessix或Harnessix Code名称、Logo及品牌标识使用权；品牌规则由`TRADEMARKS.md`定义。
7. 外部贡献默认按AGPL-3.0-only提交。为了保持商业双许可能力，合并前还必须接受`CONTRIBUTING.md`中的附加许可授予；不能证明权利来源的代码不得合并。
8. 直接和传递依赖的许可证、版权通知与发行物SBOM分别由`THIRD_PARTY_NOTICES.md`及0.9供应链门禁管理。
9. 不使用自定义“MIT但禁止商用”“AGPL但禁止竞争”等附加限制；需要不同权利时只通过单独签署的商业许可证授予。

## 结果

### 正向结果

- 闭源分发和修改后网络托管受到标准强Copyleft义务约束；
- 社区仍可查看、使用、修改、评测和贡献代码；
- 版权所有者保留向特定客户提供闭源商业授权的能力；
- 许可证、版权、商标和第三方通知的边界独立且可审计。

### 成本与风险

- 已经按MIT取得的历史版本仍可被继续使用，不能通过本决策追溯撤销；
- AGPL可能降低部分企业、插件作者和闭源集成方的采用意愿；
- 双许可要求持续维护清晰的贡献权利链，未取得附加许可的贡献不能进入商业授权版本；
- 许可证不能阻止他人独立实现相同思想，也不能替代商标、商业秘密和发布速度形成的竞争优势。

## 被否决方案

### 继续使用MIT或改为Apache-2.0

两者都允许闭源复制、修改、再分发和商业托管，不能满足当前Copyleft目标。Apache-2.0的明确专利授权有价值，但不解决闭源复用问题。

### 使用GPL-3.0-only

GPL能够约束分发的衍生版本，但通常不能覆盖仅通过网络提供修改版本而不分发副本的场景。

### 使用自定义非商业或禁止SaaS许可证

该方案可能更直接限制竞争使用，但不属于标准开放源代码许可证，会增加兼容、采用和解释成本。
