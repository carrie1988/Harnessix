# ADR 0145 大仓库的整仓搜索

- 状态：评审中
- 日期：2026-11-12

## 背景

0.10.0b20真实仓库复测（B20-05）：在vLLM仓库（6,682个受跟踪文件、101.6 MB）的根目录搜索一个标识符
（`grep {"query": "report_build_time_ninja", "max_results": 20}`），5秒后报`tool_timeout`，没有任何结果；
测试者手工指定目录后任务才继续。报告把它记为单次观察。

复核后它是必现的：

- 快照与正则搜索的总读取上限是64 MiB，而这个仓库的文本超过它；不设时限时搜索读到64 MiB即以
  `limit_exceeded`结束。
- 设了5秒读取时限时，读完64 MiB之前就超时。同一查询`git grep`用0.36秒。
- 时间花在哪里（解除上限后整仓扫描约8.4秒）：约六成在`_decode`逐字符判断是否含控制字符的Python循环；
  约四分之一在对每个文件逐行调用匹配器，即使这个文件根本不含查询；每个文件还要计算一次正文摘要。

## 决策

1. **二进制判断改用一次正则扫描。** `tools/files.py::_decode`用预编译的字符类
   `[\x00-\x08\x0b\x0c\x0e-\x1f\x7f]`查找控制字符，结论与原逐字符判断逐一相同；读文件、搜索、Git读取都受益。
2. **整份文本不命中的文件不逐行扫描**（只对快照与正则搜索）。先把同一个匹配器用在整份文本上，不命中就跳过
   逐行扫描和摘要计算。成立条件由`grep_matcher.whole_text_decides`判断：
   - 字面量查询：查询不含控制字符，命中不会跨行；
   - 不含行首行尾与文本首尾锚点（`^`、`$`、`\A`、`\z`）的正则：RE2没有前后查找，一行内的命中在整份文本的同一
     位置同样成立，单词边界在行首行尾两侧的结论相同；整份文本可能多出跨行命中，那只是多做一次逐行扫描；
   - 含上述锚点的正则不走捷径，照旧逐行判断（例如`needle$`在CRLF文件里只有去掉回车后的行才命中）。
3. **超长行只在可能命中的文件里计数。** 超过单行上限的行不参与匹配，原先一律记为缺口。整份文本都不含查询的
   文件，其超长行藏不住命中，不再计入`long_lines`，这类搜索可以如实报告`scan_complete`。
4. **整仓上限放宽到四倍。** 快照与正则搜索：目录条目50,000→200,000，名称字节8→32 MiB，总读取64→256 MiB；
   单文件上限仍是2 MiB。能搜多大的仓库由读取时限决定，而不是由这组上限决定。
5. **原字面量合同不变。** `GrepInput`及其执行合同（`bounded-search/v3`）、描述符摘要、统计口径逐字节不变；
   它只得到第1点带来的提速。快照与正则搜索的执行合同版本由v5、v6改为v7、v8。
6. **读取时限不变**，仍是5秒。

## 效果

vLLM副本、产品默认时限与上限、空闲机器：

| 查询 | 0.10.0b20 | 本ADR |
|---|---|---|
| `report_build_time_ninja` | 5.00秒超时，无结果 | 2.46秒，7处命中，完整扫描 |
| `SummarizeEntries(entries)`（正则无命中后按字面量回退） | 5.00秒超时，无结果 | 2.15秒，2处命中 |
| `class \w+Error\b` | 4.93秒 | 1.48秒 |
| `^def main`（含锚点，逐行） | 0.49秒 | 0.41秒 |

## 没有解决的

- 比这大得多的仓库（数百MiB文本）仍会撞上5秒时限，模型得到“缩小path”的提示而没有部分结果。要在超时或
  超限时返回已找到的命中，需要修改搜索输出合同（截断原因、零命中时的截断语义），另行设计。
- 每个文件都从文件系统根重新逐级打开并核对工作区根身份，这部分约占剩余时间的一半。它是读工具防止根目录被
  替换的安全设计，本ADR不动。
- Glob仍使用原字面量合同的上限（10,000个条目）。
