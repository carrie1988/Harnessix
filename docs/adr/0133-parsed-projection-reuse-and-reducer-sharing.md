# ADR 0133 Thread投影的解析复用与Reducer结构共享

- 状态：评审中（两项决策都改变了此前写明的做法，需产品负责人批准后转为现行）
- 日期：2026-11-11

## 背景

SWE-bench Multilingual评测中，Harnessix自身每个模型步骤耗时约1.4秒，而且随步数线性增长：
`preparing_context`在第1–10步是0.15秒，第90步以后是1.4秒；mini-swe-agent这部分接近零。

用脚本化模型驱动产品运行时的本地基准（`scripts/host_step_overhead_bench.py`，60步、每步一个工具
调用、结果1–3 KB，装配与评测相同）复现了这一增长：第51–60步每步约1.2秒，几乎全部是事件循环线程的
CPU时间。逐处计时的结果（60步合计59秒）：

| 位置 | 次数 | 合计 | 原因 |
|---|---|---|---|
| `verify_snapshot`与`_validated_snapshot`各解析一次Thread投影 | 6,624 | 19.8秒 | 每次读取都把整份投影解析两遍；一步有约55次读取 |
| `apply_event`深拷贝整个Thread | 1,019 | 7.1秒 | 每追加一个事件拷贝一次全部历史 |
| `save_projection`序列化整份投影 | 872 | 1.4秒 | 每次提交重写完整投影 |
| 出站请求与公开输出的密钥扫描 | 17,579 | 2.9秒 | 其中出站请求每步扫描一次完整请求 |

投影随历史增长，所以前两项的单次代价与历史长度成正比，一步的代价就是“读取次数×历史长度”。
读取来自运行时自身（每次提交前读一次、事务内再读一次）和协议客户端的轮询（每个事件一次）。

此前的设计（M09-R4详细设计第7.1节、Session模块设计）明确规定同一次读取只复用原字节，
“不缓存认证或解析模型”，第二个校验器重新解析；Reducer自0.3.1起在每个事件后深拷贝整个Thread。
本ADR修订这两处。

## 决策

### 1. 解析结果按原字节摘要复用

`SQLiteSessionStore`持有一个进程内的`ParsedProjectionCache`：按Thread记住最近一份
“原字节SHA-256与投影版本→已解析并通过内容校验的Thread”。

1. **每次读取照常做完全部存储侧校验。** 取回原行、编码一次、认证侧SHA与签名检查点比对、检查点MAC、
   事件数量与链尾哈希、存储侧SHA与行内摘要比对、序号与身份比对，一项不少，顺序不变。
2. **只省去解析。** 本次读到的原字节的SHA-256与投影版本都与记录相同时，复用已解析的Thread，
   跳过JSON解析、版本内容校验和拒绝闭合校验。这三步是原字节与版本的纯函数，摘要相同即结果相同。
3. **不记失败、不由写入方预填。** 只有解析并通过内容校验的结果进缓存；追加之后的第一次读取仍从
   数据库读回的字节解析，不拿内存中的Thread代替，所以不依赖“序列化再解析等于原对象”。
4. **不走缓存的路径。** 进程启动时的全库恢复扫描仍对每份投影解析两次。认证历史读取
   （`authenticated_thread_history`）仍用完整事件重放结果与投影比较。
5. **范围。** 每个Thread只留最近一份，最多16个Thread，超出时淘汰最久未用的；只在内存中，进程退出即失效。

### 2. Reducer不再深拷贝整个Thread

`apply_event`返回的Thread与输入的Thread、事件共享未变化的子对象。Thread聚合内全部是冻结模型，
共享不改变任何取值。Store边界的值拷贝不变：追加前仍把调用方的Draft经JSON往返冻结。

## 安全边界

- **认证没有减弱。** 每次读取交付的Thread，其原字节都在本次读取中重新读出、重新计算摘要并与签名
  检查点比对；缓存不保存也不替代任何认证结论。与ADR 0126不同，这里没有“本次不重验”的数据。
- **摘要不同就不复用。** 数据库中的投影被改写后，认证Store因摘要与检查点不符而拒绝；无认证Store
  按原设计只核对行内摘要，一致的改写返回新字节的解析结果，不返回缓存的旧对象。
- **新增的约束：共享对象不得原地修改。** 命中缓存时多个读取方拿到同一个Thread对象，Reducer的结果又与
  它共享子对象。字段赋值已被冻结模型禁止，但`arguments`、`output`这类JSON容器在Python层面仍可变；
  任何代码原地修改它们，都会让同一进程内其他读取方看到被改过的值，直到该Thread下一次提交。
  持久数据不受影响：写入的字节来自Reducer的结果，下一次未命中时从数据库重新解析。
- **对这条约束的核实。** 仓库内没有对Thread内JSON容器的原地修改（工具执行前已深拷贝调用）；
  用“每次命中都重新序列化并与记录时比对”的检查器跑过session、agent、artifacts、app_server四个
  测试目录，没有发现修改。这是当前代码的证据，不是机制保证。

## 考虑过的其他做法

- **只去掉同一次读取内的第二次解析。** 没有共享对象的问题，但一步仍有约55次解析，只能省一半。
- **不读正文，只比对检查点Seal。** 更快，但投影正文在进程运行期间被改写时要到下一次全量读取才发现，
  属于减弱校验，未采用。
- **减少运行时的读取次数**（提交前不再读取、合并提交）。改动运行时的调用顺序与崩溃恢复测试，
  范围大，留作后续。
- **Reducer保留深拷贝，改用更快的拷贝方式。** JSON往返约为深拷贝的一半耗时，仍与历史长度成正比。

## 后果

- 本地基准（60步，三轮交替取最好的一轮）：每步平均763毫秒降到377毫秒；第51–60步从1,196毫秒降到
  540毫秒（只做第1项是719毫秒）。Thread解析从6,624次降到872次，Thread深拷贝从1,019次降到0。
- 每步代价仍随历史增长：每次提交后解析一次、序列化一次整份投影，出站请求每步完整扫描一次。
  0.5秒的目标在第51–60步尚未达到。
- `tests/session/test_read_original_bytes.py`原先断言单条读取解析两次，现改为解析一次；
  恢复扫描的断言不变。M09-R4详细设计第7.1节关于“不复用已解析模型”的表述需同步修订。
- 回退：删除缓存参数即恢复每次解析两遍；恢复`deep=True`即恢复深拷贝。两者互不依赖，不涉及数据库、
  Seal、协议或配置。
