# ADR 0141 CRLF与混合换行文件上的精确编辑

- 状态：评审中
- 日期：2026-11-12
- 来源：第2轮分支`feat/round2-time-and-resolve`的ADR 0129第2版第7节中关于换行的部分（提交`dc508e4e`）。
  产品负责人要求这项修复先于第2轮其余内容从主线发布，所以在主线单独成文；第2轮分支带有同样的行为，
  合入主线时改为引用本ADR。

## 背景

真实用户Beta测试（PyPI 0.10.0b12，macOS终端界面，百炼qwen3.8-flash，两轮共385个模型步骤）中，85次工具契约错误
有68次来自`apply_patch_batch`，其中`patch_context_not_found` 32次。

- **多行编辑在CRLF区永远匹配不上**（RT-06，`state-ocr`事件594–726）：目标文件是混合换行（804行CRLF、524行LF），
  被改的函数在CRLF区。`read_file`把原始字节逐行解码后交给模型，正文带着`\r\n`；模型发回的`old_text`内容逐字正确，
  换行却是`\n`。规划器只做逐字节匹配，连续5次拒绝，期间没有人改过文件。
- **诊断把换行差异说成内容不一致**：缺失诊断用`strip()`比较首行，`\r`被去掉，于是得出“首个非空行出现在第724行，
  但其后内容不一致（可能已被此前的Patch修改）”。模型据此反复重读、重发。
- **单行锚点命中后写出混合换行**（事件726）：`new_text`里的`\n`被原样写进CRLF区。测试通过后，模型又花了约2分钟
  修这些换行，其中一次编辑误删函数头后自行回滚（事件987–1086）。
- **模型发回的换行风格并不可靠**：同一处编辑，事件594的`new_text`是`\r\n`，事件684是`\n`；事件987、1029的一条
  `new_text`里两种换行混用；事件744把带`\r\n`的新行写进了LF区，事件1079再用一条只改换行的编辑把它们改回LF。

Windows项目的文件多为CRLF，这个缺陷对Windows用户的影响面最大。

## 决策

### 1. 匹配：先逐字节，其次忽略CRLF/LF差异

1. 逐字节匹配仍是第一步，判定不变：恰好一处就用它，多处按锚点不唯一拒绝。逐字节恰好命中一处时不再做
   忽略换行的匹配；区间除第4条的情形外与此前相同。
2. 一处也没有时，把文件与`old_text`里的`\r\n`都折成`\n`再匹配一次，命中位置映射回原始字节区间；映射出的区间
   总是覆盖完整的`\r\n`，不拆开换行。忽略换行后恰好一处才接受；多处同样按`patch_ambiguous_context`拒绝，
   不按“哪一处的换行更像”从中挑选。
3. 只折叠`\r\n`：孤立的`\r`不算换行，照旧逐字节比较。
4. 以`\n`开头的`old_text`逐字节命中`\r\n`的后半时，区间向前多取一个字节把`\r`纳入。否则按第2节改写换行会写出
   `\r\r\n`，删掉这个换行则留下孤立的`\r`。

重叠检测、无变化判定与大小上限都在原始字节区间上进行，与此前相同。

### 2. 写入：换行风格由文件决定

`new_text`里的换行（`\r\n`或`\n`）一律按被替换处的风格写入，CRLF处保持CRLF，LF处保持LF：

| 被替换的区域 | 采用的风格 |
|---|---|
| 含有换行 | 区域内占多数的一种；两种一样多时取区域内第一个换行 |
| 不含换行 | 所在行的行尾；所在行是没有行尾的末行时取上一行的行尾 |
| 整个文件没有换行 | 不改写，按`new_text`原样写入 |

- 逐字节命中的编辑同样适用：单行锚点换成多行文本，正是Beta里写出混合换行的那条路径。
- 例外只有一个：折叠换行后`old_text`与`new_text`相同的编辑，唯一可能的意图是转换换行，按原样写入（事件1079）。
  这样的编辑若只在忽略换行时命中、而文件已是`new_text`的样子，结果是如实的`patch_no_change`。
- 不按“模型是否写了`\r`”区分有意与无意：背景里的证据表明带`\r\n`抄下`old_text`的同一条编辑，`new_text`照样
  混用两种换行。

### 3. 诊断

锚点缺失的说明沿用主线现有的中文措辞与三个分支，只改与换行有关的事实：

- 比较在折叠后的正文上进行。走到诊断时已确认忽略换行也找不到，所以换行差异不会再被说成内容不一致。
- “此编辑可能已经应用”的判定同样忽略换行：上一次写入已按文件风格改成`\r\n`，模型重发时带的是`\n`。
  说明由“new_text已原样存在于当前文件”改为“new_text已存在于当前文件（不计CRLF/LF换行差异）”。
- 首个非空行仍在文件中的分支不再断言“其后内容不一致”（该比较忽略首尾空白，单行锚点只差缩进时也会走到这里），
  改为陈述宿主核对到的事实：“old_text首个非空行（不计首尾空白）出现在当前文件第N行，但old_text与该处内容
  不一致，且不只是CRLF/LF换行的差异”。
- 行号统一按`\n`计数，与`read_file`的分页一致（原先这一分支用`splitlines()`，孤立的`\r`会让行号偏移）。

### 4. 已保存的计划

`delivery/trusted_action.py`的`_validate_mutation`与受管Patch的`validate_prepared`会用“前镜像加编辑”重算后像，
核对已保存的计划；执行、对账和回滚都先经过这一步。第1、2节改变了部分编辑的重算结果（如事件726那样的事务），
所以复核时传入计划记录的后像摘要（`apply_exact_edits(recorded_sha256=...)`）：按本ADR之前的语义
（只逐字节匹配、`new_text`原样写入）算出该摘要的计划照旧通过，否则按当前语义重算并照常比较。两种语义都算不出的
后像仍被拒绝。没有这一步，升级前发布的这类修改在升级后无法回滚（回滚的Turn会中断）。受管Patch的结构化Diff
用同一组区间。

### 5. 不变的部分

- 批次仍是原子的；`expected_sha256`、事务前后像与结果里的`content_sha256`都按文件的真实字节计算。
- 审批绑定的仍是模型发来的调用，审批预览与Diff来自按上述规则算出的事务前后像。
- 回滚、恢复、`old_text`与`new_text`相同的拒绝、编辑重叠检测、各项上限不变。
- create与replace写入的字节不变；公共Schema、事件、`spec/`与产品配置不变。
- 拒绝说明的语言与结构不变（中文、不带`edits[j]`下标）；锚点不唯一与编辑重叠的说明原文未动。

## 与第2轮分支的关系

第2轮分支在ADR 0129第2版第7.2–7.4、7.7节实现了同样的匹配、写入与已保存计划的规则，本ADR的规划器代码由它移植而来。
一并移植的还有补SHA时的唯一性判定（见下一节）。以下内容属于第2轮，不在本次移植范围内，主线行为不变：

- 英文的拒绝说明、`edits[j]`下标与各处行号，以及整批未应用的说明。
- 第2轮在补SHA上的其他扩展（replace与delete从历史补摘要、缺`path`时按摘要补路径等）。

## 补SHA时的唯一性判定

主线的提案修复（`agent/call_repair.py`的`_anchored_sha256`）在edit的`expected_sha256`缺失或过期、而每段`old_text`
都在当前文件中唯一出现时，替模型补上当前文件的SHA-256。此前“唯一出现”只按逐字计数，CRLF文件上的多行LF锚点
计数为0，不补，调用随后因SHA不符被拒。现在与规划器同一顺序判定：先逐字计数，一处也没有时忽略CRLF/LF差异再计数，
都要求恰好一处。规划器仍是最终裁决，补上的SHA在规划与执行前照常核对。

## 未做与已知边界

- replace用`\n`正文整文件替换CRLF文件时，整个文件变为LF。它不产生混合换行，且`content`的摘要绑定在审批Route上，
  改写写入的字节需要改审批绑定，本版未动。
- 混合换行文件里同一段文字以两种换行各出现一次、`old_text`逐字节只命中其中一处时，按逐字节命中的那处应用，
  与此前相同；模型若本想改另一处，要从结果里的Diff发现。改为“只要忽略换行后不唯一就拒绝”会改变逐字节路径的
  现有结果，留作后续决定。
- 孤立的`\r`（旧Mac换行）与`\r\r\n`不做处理。

## 后果

- CRLF处写入的字节比模型发来的`new_text`多（每个换行多一个`\r`）；Diff、结果摘要与后续`expected_sha256`都以
  真实字节为准。
- 模型在LF处有意写入的`\r\n`会被写成`\n`，除非该编辑只改换行。
- 逐字节路径上，以`\n`开头并命中`\r\n`后半的锚点，其区间起点比此前早一个字节。
- 升级前保存或发布的计划照旧可以执行、对账与回滚；复核多做一次按旧语义的重算，只发生在带edit的已保存计划上。
- 记录的后像摘要要经`delivery/trusted_action.py`的`_apply_workspace_exact_edits`传给规划器，签名、调用与
  `_validate_mutation`的调用处共多出4行。该文件在可读性策略里的上限（622行）没有调高：同一文件里一处被拆成
  六行的调用合成了一行，文件由621行变为620行。规则本身都在`patches/planner.py`，`trusted_action.py`没有新增职责。

## 验证

- 补SHA：`tests/agent/test_call_repair.py`（只差换行的唯一锚点补当前SHA；忽略换行后不唯一的不补；逐字只命中一处的以它为准）。
- 规划器不变量：`tests/patches/test_planner_newlines.py`（逐字节路径的区间与字节不变；忽略换行的命中映射回原始区间；
  写入风格的各条规则；只改换行的编辑；忽略换行后的唯一性；孤立的`\r`；重叠；诊断；真实字节摘要；升级前保存的计划）。
- Delivery与产品路径：`tests/delivery/test_trusted_action_patch.py`（CRLF文件上的事务前后像与执行；升级前保存的事务
  仍可加载与执行）、`tests/product_config/test_product_patch_rollback.py`（升级前发布的修改仍可回滚）、
  `tests/product_config/test_patch_newlines.py`（由Beta现场缩减的回归：混合换行文件、多行LF锚点、后续单行编辑、
  原样抄回`\r\n`的编辑）。
- 现场重放（一次性核对，脚本不在仓库内）：0.10.0b20真实仓复测中未改动的混合换行文件（804行CRLF、524行LF）与当时
  被拒的那次补丁。0.10.0b20源码上结果是`patch_context_not_found`；改动后应用成功，CRLF行由804变为817，LF行仍是524。
- 新增测试在未改动的0.10.0b20源码上失败；关掉“按记录的后像摘要复核”后，四项升级兼容测试失败。
- 未在Windows上运行：改动只处理字节串，没有平台分支。
