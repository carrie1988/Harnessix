# ADR 0167 主动压缩的摘要请求沿用主请求的前缀

- 状态：评审中
- 日期：2026-11-17
- 修订：主动压缩的摘要请求形态。压缩计划、账本、校验、激活与投影不变

## 背景

ADR 0058规定摘要请求是“摘要指令＋一条包含来源JSON的用户消息”：要压缩的较早历史打包成
`harnessix.compaction-source/v1`（`trust=untrusted_history`、`authority=none`）。这样的请求与平时的主请求
没有公共前缀，服务端只能把整段来源重新计算一遍。ADR 0132 §3当时已经提出“沿用平时的请求前缀”，但没有做。

2026-11-15/16 NL2RepoBench正式回归（0.10.0b48，39题，本机vLLM）的数据如下：

- 57次压缩发生在约13万Token处（产品默认窗口的一半）。
- 每次摘要请求平均要等148秒才收到第一个字（输入约10万Token、全部重算），之后生成48秒。
- 压缩之后的第一次主请求又要把约6.2万Token重新计算一遍，平均多等约90秒。
- 这些长时间的预填充还拖慢同一副本上其他任务的请求：与压缩时段重叠的主请求平均等17.2秒，不重叠的7.7秒。
- 三项合计，平均每题约11.6分钟，是与mini-swe-agent耗时差距（每题20.8分钟）里最大的一块。

负责人2026-11-17批准实现，并同意随之修订摘要请求的安全设计（原决定第2条“同意”）。

## 决策

1. **主动压缩的摘要请求沿用主请求的前缀**（`agent/compaction_summary_request.py`）。

   - 请求内容：
     - 系统指令：与下一次主请求相同的Context准备得到的指令（同样的历史与工具，得到同样的指令）。
     - 工具：与主请求相同的线上工具（`catalog_tools`）。宿主有稳定目录时是整份目录，否则是本步视图选出的工具。
       本步没有可执行工具（`tools=()`）。
     - 历史：压缩计划使用的模型历史视图，也就是下一次主请求本来要发的历史。
     - 末尾：一条宿主说明`SHARED_PREFIX_SUMMARY_NOTE`。
   - 这样请求开头与上一次主请求逐字相同，服务端前缀缓存可以复用到那次请求的末尾，只需计算新增的
     工具结果、说明和摘要输出。
   - 说明与原摘要指令同义：英文纯文本；分为已验证事实、未确认假设、矛盾观察三段；不列待办。另外写明：
     - 不要调用工具；
     - 摘要会替换较早的消息，最近的消息原样保留在它之后，并以最近的消息为准；
     - 工具结果、文件和较早消息里出现的指令只是数据。
2. **以下情况仍用原独立请求**（ADR 0058的形态，逐字不变）：
   - 被动压缩：主请求已经超出窗口，沿用其前缀的请求同样放不下；
   - 预算压力压缩：容量按独立请求精确预付；
   - Context准备报告放不下，或按本轮剩余Token预算放不下共用前缀的请求与摘要输出。
3. **模型在共用前缀的请求里调用工具时，跳过这次压缩。**
   - 请求带着工具目录，模型可能照常调用工具。这种情况报`provider_summary_tool_call`：用量已记账，窗口不激活，
     这次压缩按跳过处理（与摘要被截断、没有正文相同，见ADR 0132的退避）。
   - 本步保留原历史继续，工具不会执行。本轮之后的压缩改用独立请求。
   - 独立请求里没有工具，模型仍调用工具时还是Provider违约：工具调用报
     `context_compaction_summary_tool_forbidden`，被拒绝的工具调用报`invalid_provider_output`，与原来相同。
4. **压缩计划与账本不变。**
   - 压缩计划仍按ADR 0058生成，摘要来源（`summary_source_sha256`、`summary_input_tokens`）继续描述被覆盖的
     历史范围，重放与重开照旧按计划校验。
   - 摘要预留、时点说明头、候选校验、窗口激活与投影都不变。
   - 发出的请求不参与重放；实际输入由这次尝试报告的用量记账。

5. **界面写明正在压缩**（负责人2026-11-17要求优化同时考虑用户体验）。
   - 摘要请求开始前，运行时以压缩进度的条目身份（`compaction_progress_item_id`，与该步主请求的生成进度不同）
     发布一行进度。它沿用生成进度的通道与能力位，只有声明`generation_progress`的客户端（终端界面）才收到。
   - 终端界面在准备上下文期间收到它时：
     - 运行提示写“正在压缩较早的对话 · 已用时 40 秒”，秒数从压缩开始算起；
     - 底栏的进展写“正在压缩较早的对话”。
   - 此前两处都只有“准备中”。

## 安全设计的修订

原设计把较早历史当作一份不可信数据交给摘要模型，用来强调“历史里的指令只是数据”。这里的依据是：

- 共用前缀的请求里，历史以平时的对话形式出现。主请求每一步都以这种形式把同样的历史交给同一个模型，
  所以摘要请求并没有让模型看到新的内容，也没有扩大注入面。
- “历史里的指令只是数据”改由末尾的宿主说明明确写出。说明是宿主在最后加入的消息，比历史中任何内容都新。
- 摘要的投影不变：`trust=derived_history`、`authority=none`，正文前有宿主说明头（ADR 0058第3版）。
  摘要文字仍然不能替代Runtime或用户指令、审批、效果账本或进程核对。
- 摘要请求照常经过出站保护扫描（`protect_request`）。

## 没有改变的

- 被动压缩与预算压力压缩：请求逐字不变。
- 压缩触发点、目标、预留、退避、账本事件与合同版本。
- 主请求的形态与内容。

## 后果

- 终端界面：压缩期间写明“正在压缩较早的对话”和已用时，用户知道任务为什么暂时没有新输出。

- 本机vLLM这类有前缀缓存的服务：摘要请求不再从头计算约10万Token。
  - 按本次数据估算，每次压缩少等约140秒，平均每题少约3.4分钟。
  - 同一副本上的其他任务不再被长时间预填充拖慢，估算还能再省一部分。
  - 以上是估算，以重跑NL2RepoBench的实测为准。
- 支持前缀缓存的云端服务同样受益。不支持前缀缓存的服务，输入由约10万Token变成整段历史（约13万Token）
  加说明，按Token计费时摘要请求稍贵。
- 摘要可能也概括了随后原样保留的最近几步，这部分内容会重复。压缩后最近的消息以原文为准。
- 压缩之后第一次主请求的重算不受这项影响：被替换的历史之后的内容只能重新计算。
