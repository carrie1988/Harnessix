# ADR 0148 交互模式的运行时间检查点与一键收尾

- 状态：评审中
- 日期：2026-11-12

## 背景

每个Turn有一份墙钟预算，产品客户端传入1小时；到时内核把Turn判为失败（界面显示“未完成”），等待用户审批的时间
也算在内。负责人在已安装的0.10.0b20上做了一次真实试用（从零创建一个演示黑洞的3D网页，百炼qwen3.8-flash）：

- 第一轮在整60分钟时被时限终止，其中包含14次等待审批的时间；网页在这之前已经写出来了。
- 用户只能输入“继续任务”重新开始一轮，四轮共126分钟。
- 网页写完之后模型一直在自己追加验证和修改（43条命令），用户想让它停下来给个结论，只有“取消”（没有总结）
  和用`Ctrl+S`自己写一段话两个办法。

终端界面是有人在场的使用方式：时限的本意是防止没人看着时一直运行，而不是在用户看着的时候把任务判为失败。
负责人的决定：实际运行满60分钟时询问是否继续，等待审批的时间不计；无人值守（`harnessix exec`）保持不变；
并提供一键收尾，在询问里也给出收尾的选择。

## 决策

1. **交互模式不再由内核墙钟预算在第60分钟终止任务。** 终端界面发起Turn时，墙钟预算取协议允许的最大值
   （86,400秒），仅作为最后的兜底；步数上限（100步）与累计Token上限的规则不变。无人值守的预算不变（1小时）。
2. **界面自己累计任务实际运行的时间，按Turn计。** 只有Agent自己在工作的状态计时
   （已接受、准备上下文、调用模型、执行工具、收尾）；等待审批、等待用户操作、等待用户回答不计。
   计时只在界面进程内，不写入会话记录；新的Turn从零开始。
3. **实际运行每满60分钟询问一次**（其他窗口打开时等它关闭后再问），任务在询问期间照常运行：
   - **继续**：重新计时，再满60分钟时再问。
   - **收尾**：向正在运行的任务发送固定的收尾说明（见第6条）。
   - **停止**：取消当前任务，与`Ctrl+X`相同。
   - 按`Esc`关闭窗口等同于继续：关闭窗口不等于停止任务。
4. **5分钟内没有选择，先暂停本轮**（取消当前Turn，已完成的修改保留），询问窗口留在屏幕上并改为说明已暂停。
   用户回来后的选择从新的一轮开始：继续发送“继续完成上一轮没有做完的任务。”，收尾发送要求直接给出总结的说明，
   停止（或`Esc`）就停在这里。
5. **询问期间任务自己结束了，窗口自动关闭**，不把已经完成的任务当成暂停处理。
6. **一键收尾（`Ctrl+F`）**：替用户向正在运行的任务发送一条固定的补充说明——不要再做新的修改或检查，
   直接给出最终总结：已经完成了什么、哪些没有来得及做、哪些没能验证需要用户自己确认。它与`Ctrl+S`走同一条
   通道，模型在下一步看到；任务不可补充说明时不可用。

## 取舍

- **计时放在界面，不放进内核。** 内核里实现“等待审批不计时”要改Turn与预算的持久化模型和协议合同
  （新增累计等待时间、改时限的判定与恢复后的重算），这两处的模块规模已经在可读性预算的上限，而且与正在进行的
  第二轮开发改同一批文件。界面侧实现不改任何持久化结构与协议，代价是：
  - 计时不跨界面重启：重新打开界面后从零开始；
  - 只对界面当前显示的会话计时；
  - 暂停是通过取消Turn实现的，界面显示“已取消”，继续时是新的一轮，模型从会话记录里接着做。
  24小时的内核预算保留为兜底，覆盖上述几种没有被界面计时的情况。
- **无人回应时暂停而不是继续运行。** 有人在场是放宽时限的前提；没有人回应就回到原来的保护，
  但保留已完成的修改，并让用户回来后一步就能接着做。
- **收尾是对模型的请求，不是强制。** 正在生成的一步会先做完，模型在下一步才看到说明；（第2版起由宿主保证，见第“修订”节。）
  需要立即停下时仍然用`Ctrl+X`。
- 没有采用“满60分钟自动收尾”：任务是否做完由用户判断，自动收尾会打断确实需要更长时间的任务。

## 后果

- 终端界面里，长任务不再在第60分钟显示“未完成”；用户每60分钟的实际运行时间被问一次，等待审批多久都不影响。
- 用户不在场时，任务最多在实际运行60分钟后再运行5分钟就暂停。
- 无人值守、评测与SDK调用方的行为不变。
- 用户手册里“等待审批的时间计入任务时限”的说法只对无人值守成立，随本次修改更新。

## 修订（第2版，2026-11-13）：收尾由宿主保证

0.10.0b24 macOS Beta复测（GitHub Issue #4）：测试刚通过、模型正准备下一步时按`Ctrl+F`，界面显示收尾说明已进入会话，
模型仍读了README、运行了`--help`与缺参检查，约53秒后才结束。第1版的“收尾是对模型的请求”在这里不够：说明只在下一步被
模型看到，模型也可以不照做；更新记录却写了“停止追加工作”。

决定：说明一旦记入本轮，由宿主保证不再发起新的修改或检查（`product_config/wrap_up.py`）。

- **判定只看持久事实：** 本轮有一条用户消息（含运行中补充的说明）正文等于两段固定收尾说明之一
  （`WRAP_UP_STEER`：`Ctrl+F`与检查点询问时的“收尾”；`WRAP_UP_PROMPT`：检查点暂停后选“收尾”开的新一轮）。
  界面发送的文本与宿主判定共用同一份常量。恢复重放得到相同结论。
- **之后的步骤不提供任何工具**（`WrapUpToolView.select`返回空的工具集）：请求里不再带`tools`，模型只能给出总结。
  百炼qwen3.8-flash与DeepSeek的真实接口都接受“历史里有工具调用、本次不带工具”的请求并给出总结。
- **尚未开始、经审批边界的调用不执行**（`WrapUpToolView.admit_call`）：命令、修改、可信Action等在审批或执行之前以
  `tool_wrap_up_requested`结束，如实回给模型“你已要求收尾，这次调用没有执行”。不经审批边界的只读读取在同一步里照常完成
  （毫秒级）；拒绝它们需要改运行时内核，收益很小，没有做。
- 产品装配始终安装这个视图：通用执行时它包住“提供全部工具”，编码阶段视图时包住原视图；没有收尾时选择结果与原来相同。

验证：`tests/product_config/test_wrap_up_stops_work.py`（模型正在生成时补充说明：已提出的命令不执行、下一步0个工具、以总结结束；
已提出的只读读取照常完成但之后不再提供工具；其他补充说明不影响；检查点“收尾”开的新一轮从一开始就不提供工具；界面文本与宿主常量一致）。
真实终端界面（tmux，模型换成在第1步扣住4秒后提出一条沙箱外命令的脚本，第1.5秒按`Ctrl+F`）：修复后命令以“你已要求收尾”
未执行、第2次请求0个工具、以总结结束；修复前的代码上同一命令照常进入“等待你审批”，第2次请求仍有12个工具。

## 修订（第3版，2026-11-13）：收尾时已经在等审批的操作

发布会话在Windows真机上复测第2版（3/3）：按`Ctrl+F`时，第3步的`python -m unittest`已经提出、审批请求已经建立，审批窗口还没弹出
（自动弹出有2秒延迟）。收尾说明记入之后窗口照常弹出，批准后命令照样执行，第4步才以总结结束。原因：调用准入只在建立审批请求之前
检查一次，审批请求已经存在时不再经过它。Linux上沙箱内命令不需要审批，没有这个窗口。

决定：终端界面在本轮记入收尾说明后，把还在等待的审批直接拒绝（`approval_automation.auto_approve_pending`，原因“你已要求收尾，
这次操作不再执行”），并且不再自动弹出这条审批的窗口（`interaction_presenter`）。拒绝总是安全的，不需要先满足批准所需的证据条件。
判定与宿主共用同一份收尾文本（`product_config/wrap_up.WRAP_UP_TEXTS`）。

验证：`tests/product_ui/test_wrap_up.py::test_wrap_up_rejects_an_approval_still_waiting_for_its_dialog`（修复前该轮一直停在等待审批）；
真实终端界面（tmux，脚本模型立即提出一条需要审批的沙箱外命令，1秒后按`Ctrl+F`，窗口尚未弹出）：修复前停在“等待你审批”，
修复后审批记为“已拒绝：你已要求收尾，这次操作不再执行”，第2次请求0个工具，以总结结束，命令没有执行。

## 修订（第4版，2026-11-13）：收尾之后模型仍发出工具调用

0.10.0b36正式测试（macOS，百炼qwen3.8-flash）：按`Ctrl+F`时等待中的审批被正确拒绝，但之后第3～6步模型在不带工具的请求里
仍4次发出工具调用，每次只得到“工具未注册”（`unknown_tool`），第7步才给出总结；没有执行任何操作，但多了4次请求。本机复现：
同一场景（沙箱不可用、模型先提出一条沙箱外命令、等待审批时按`Ctrl+F`）11次中2次出现，分别多出6次与4次请求（约半分钟）；DeepSeek没有出现。
请求末尾的工具目录说明只写了“没有可调用的工具”，没有说明原因，拒绝结果“工具未注册”也不告诉模型该做什么。

决定：`WrapUpToolView.select`在收尾之后返回空目录时附上说明`WRAP_UP_NOTICE`（“用户已要求收尾：这一步不提供任何工具，任何工具调用
都不会执行。请直接用文字给出最终总结……”），经已有的`ModelToolSelection.notice`进入请求末尾的目录说明（“Why the catalog is restricted
now”）。只是提示，不改变准入与拒绝；固定的拒绝结果合同不变。

验证：`tests/product_config/test_wrap_up_stops_work.py::test_a_turn_started_with_the_checkpoint_wrap_up_offers_no_tools`（请求带上说明）；
真实终端界面（tmux，百炼qwen3.8-flash，同一场景）：修改前11次中2次在收尾后多出4～6次被拒的调用，修改后24次都在收尾后的第一次请求
直接给出总结。宿主在收尾后限制步数（连续被拒若干次即结束本轮）会让用户拿不到总结，暂不采用；再出现时另行评估。
