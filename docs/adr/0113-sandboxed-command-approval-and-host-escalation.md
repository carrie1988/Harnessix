# ADR-0113：沙箱内命令免审批与沙箱外命令

- 状态：评审中。设计已由用户在 2026-11-07 拍板（第 6 节）
- 日期：2026-11-07

## 1. 背景

### 1.1 现在的审批机制

- **交互模式下每条命令都要审批。**
  - Trusted Action 默认策略是 `DefaultCodingRiskPolicy`（`trusted_actions/policy.py`，版本 `trusted-coding-action/v1`）。
  - 凡有写入、执行或网络效果的动作一律要求审批，只有低风险的只读动作直接放行。
  - 所以无论命令在容器里还是外部边界里执行，交互模式下每条都会弹审批。
- **非交互模式按工具名前缀自动批准。** `harnessix exec --approval-mode auto` 由客户端按 `exec_command.`、`run_profile.` 前缀自动回答“批准”（`exec_cli.py`）。
- **执行链路已支持“策略直接放行”。**
  - 策略返回放行时，路由直接进入 `ready`，不产生审批请求。
  - `execution_is_approved` 对放行计划要求没有批准检查点。
  - 因此“免审批”只需改策略，不需改执行器和进程账本。

### 1.2 业界做法（2026-11-07 查证）

| 产品 | 沙箱内命令 | 需要越出沙箱（联网、写外部）时 |
|---|---|---|
| Codex CLI | 不逐条审批 | 申请越界，用户批准后执行 |
| Claude Code | 自动批准（`autoAllowBashIfSandboxed` 默认开） | 新域名弹窗询问；不经沙箱的命令按权限规则询问 |
| Cursor | 不逐条审批 | 先交判定器审查，判定器拦下而模型仍要执行时询问用户 |

- Cursor 文档写明：内核不满足沙箱要求时，退回到每条命令先征求批准。

### 1.3 用户决策（2026-11-07）

1. 沙箱内不能访问外网。需要联网时，走一个每次由用户批准的沙箱外执行通道。
2. 沙箱内命令自动执行，越出沙箱才询问。
3. 本机用不了沙箱时，命令仍可用，但每条都要批准，并标注“未隔离”。

## 2. 决策

### 2.1 沙箱内命令自动执行

**为什么不能让策略直接放行**
- Agent 内核规定：凡是声明“需要审批”的调用，成功前必须已有一条持久化的“已批准”记录（`agent/item_reducer.py`）。
- 写操作又必须声明“需要审批”（Gateway 的合同核对）。
- 因此“写操作不经审批直接成功”在内核层面是被禁止的。实测：策略返回放行时，命令执行完，但输出发布被判为“缺少批准”，整轮中断。
- 结论：审批照常产生，由 Harnessix 以系统身份当场批准。内核约束保持不变，审计能看到批准人。

**策略升为 `trusted-coding-action/v2`**：只新增一条“可由系统批准”的标记规则，其余规则和判定顺序与 v1 完全一致。
- **标记条件**（全部满足）：
  - 执行计划的 `SandboxBinding` 级别是 `host_sandboxed`，后端是 `seatbelt` 或 `bubblewrap`（ADR 0111）；
  - 执行器是命令类（`product.command-profile.*`）；
  - 资源声明只有进程执行、工作区读写、`write_roots` 对应的 `external` 写，以及 Seatbelt 的回环网络连接；
  - 没有 Secret。
  - v1 的拒绝规则（破坏性或关键风险、资源与效果不一致等）先于本规则判定，仍然有效。
- **标记结果**：仍是“需要审批”，但 `policy_id` 为 `default.approve-sandboxed-command`、原因码为 `sandboxed_command`。

**宿主自动批准**
- **钩子位置**：`AgentRuntime` 新增可选参数 `approval_responder`，默认不设置，行为与原来完全相同。产品启用了本机沙箱命令时才传入。
- **触发时机**：在 `run_turn`、`retry_turn`、`resume_turn` 三个入口的最外层，执行停在“等待审批”且应答器认可时，经公开的审批入口（`reply_approval`）落盘决定，然后继续执行。
  - 此时不持有会话锁，没有重入问题。
  - `resume_turn` 进入时先补批一次，覆盖“审批请求已落盘、系统决定未落盘时进程崩溃”的恢复情况。
- **批准前复核**：产品应答器（`product_config/sandbox_approval.py`）按 Router 持久计划再核对一次，全部满足才批准：
  - 审批上的策略 ID；
  - 计划里的策略 ID；
  - 级别是 `host_sandboxed`，后端是 `seatbelt` 或 `bubblewrap`；
  - 计划指纹一致；
  - 路由仍待批准。
- **批准人**：`harnessix:sandbox-policy`。前缀 `harnessix:` 表示系统身份。
- **客户端晚到的回复**：客户端（交互界面、`exec --approval-mode auto`、SDK、Harbor 的协议客户端）可能在“请求落盘”和“系统决定落盘”之间的毫秒级窗口里看到待审批并回复。
  - 已记录的决定来自系统身份时，结论相同的回复视为同一决定，幂等成功，审批只记一次。
  - 结论相反的回复仍报 `approval_conflict`，失败关闭；轮次本身按系统决定继续。
- **统计口径**：收据里的自动批准次数会包含这类批准。

**不变的部分**
- 容器 Profile（`container_strong`）和外部边界 Profile 本期不变，仍按原规则审批。容器命令是否同样自动批准，以后另议。
- 已按 v1 记录的路由保持原决策，不重算。
- 非交互 `exec`：沙箱内命令由宿主自动批准，与 `--approval-mode` 无关。

### 2.2 沙箱外命令

- **用途**：做沙箱内做不到的事，例如联网（安装依赖、下载、`git fetch`）或写工作区以外的位置。
- **身份**：工具名 `host_command.<profile_id>`，执行器 `product.host-command.<profile_id>`。公开输出合同与启动恢复按这一对身份识别为命令类。
  - 前缀刻意不同于 `exec_command.`。
  - 因此 `exec --approval-mode auto` 的前缀自动批准不覆盖它，Harbor 评测和非交互运行不会在无人知情时执行无隔离命令。
- **参数**：
  - `cmd`：规则与沙箱命令相同；
  - `reason`：必填，单行，最多 500 字节，说明为什么沙箱内做不到。审批时展示给用户。
- **执行**：
  - 复用 ADR 0121 的宿主执行器（`HostProcessBinding`）。
  - 执行计划如实记为 `host_guarded`、后端 `host`、网络 `full`。
  - 以工作区根为当前目录。
  - 环境按 ADR 0111 第 2.2 节的继承白名单，另外继承代理变量：国内用户安装依赖通常需要代理。
  - 不含模型凭据和 `HARNESSIX_*`。
- **审批**：每条都要用户批准。策略对 `host` 后端永远返回“需要审批”，没有任何自动批准路径。审批提示要醒目：
  - 写明“此命令将在沙箱外执行：没有隔离，可以联网，可以读写你的用户目录”；
  - 显示 `cmd` 和 `reason`。
- **模型引导**：工具说明要求先用沙箱命令；只有沙箱命令因联网或写入范围失败时，才改用沙箱外命令并写明理由。
- **资源声明**：进程执行（含 `cmd` 与 `reason`）、工作区写、网络连接（`full`）。
- **何时提供**：
  - 零配置下自动提供，前提是 POSIX Process Owner 可用。
  - 显式配置中用 `backend: "host"` 的原生 Profile 声明；不声明就没有。
- **非交互 `exec` 遇到沙箱外命令**：按现有规则交给人；无人回答时以退出码 2（`EXIT_NEEDS_INPUT`）结束。

### 2.3 沙箱不可用时

- **零配置下探测沙箱失败**（原因码见 ADR 0111 第 5 节）：
  - 不提供沙箱命令，只提供沙箱外命令，每条都要批准。
  - 启动时醒目提示：“本机沙箱不可用（原因），命令将在无隔离环境中执行，每条需要你批准”，并附修复办法，例如安装 bubblewrap 的命令。
  - 工具说明告诉模型当前没有沙箱，所有命令都会请求批准。
  - 修复后重启即自动启用沙箱，不需要改配置。
- **显式配置中声明的沙箱 Profile 探测失败**：
  - 省略该工具，并在诊断中给出原因。
  - 不自动改为沙箱外命令：显式配置代表用户的选择，不静默更换执行方式。用户可以自己在配置中加一个 `host` Profile。
- **Windows**：本期没有 POSIX Process Owner，零配置不提供命令工具（与现在相同），启动时说明原因。

### 2.4 零配置只由用户入口请求

- **怎么请求**：`harnessix code`、`harnessix code doctor` 和 `harnessix exec` 在没有指定 Action 配置时，在预检请求里置 `zero_config_actions`，并给 App Server 传 `--zero-config-actions`。两处用同一判定，生成同一份配置；不修改进程环境变量。
- **谁不受影响**：
  - 程序化启动与评测（如 Harbor 的协议客户端）不设置它，省略 Action 配置时仍是原来不含命令工具的内建配置，评测各组的工具集不变。
- **关闭方法**：用户设置环境变量 `HARNESSIX_ZERO_CONFIG_ACTIONS=0`。

### 2.5 系统指令

- 启用了本机沙箱或沙箱外命令时，使用新的“本机命令”系统指令（`harnessix.native-execution-instructions/v1`）。它写明：
  - 沙箱内命令自动执行、写入保留、无网络，不能写 `.git` 与 HOME；
  - 沙箱外命令需要逐条批准并写明理由，只在沙箱内做不到时使用；
  - 提交、分支和暂存由交付流程负责。
- 外部边界与容器使用的通用指令保持原样，评测提示不变。

## 3. 取舍

- **自动执行的剩余风险**：
  - 沙箱内命令可以改、删工作区里除 `.git` 以外的任何文件，改动保留。
  - 未提交的改动被误删后无法恢复，已提交的可用 Git 找回。
  - 主流产品接受同样的风险。
- **macOS 的回环**：macOS 放行回环（ADR 0111 第 2.4 节）。已配置的代理端口被单独拦截，但未登记的本地代理仍可能让自动执行的命令联网，从而绕过 2.2 节的批准，如实列为残余风险。
- **毫秒级可见窗口**：系统批准与审批请求是两次落盘，交互界面理论上可能短暂看到待审批。用户若在窗口内拒绝，会收到冲突提示，但轮次按系统决定继续。要彻底消除，需要让请求与决定在同一事务落盘，涉及内核与 Router 的提交顺序，本期不做。
- **沙箱外命令依赖用户判断**：弹窗频繁会让人习惯性点“同意”。用必填的 `reason` 和醒目提示缓解；“本机代理加域名白名单，让常用包源免批准联网”以后另议。
- **工具前缀不同**：换来非交互运行不会误批无隔离命令，代价是模型多一个工具要选择，由工具说明引导。

## 4. 失败语义

| 情况 | 结果 |
|---|---|
| `reason` 缺失、为空或超限 | 参数无效，沿用命令参数校验错误码，不执行 |
| 用户拒绝沙箱外命令 | 沿用现有审批拒绝结果，不执行 |
| 系统已批准后，客户端回复相同结论 | 幂等成功，审批只记一次 |
| 系统已批准后，客户端回复相反结论 | `approval_conflict`；轮次按系统决定继续 |
| 非交互运行无人审批 | `EXIT_NEEDS_INPUT`（退出码 2） |

## 5. 验收

- **交互模式**：
  - 沙箱命令不需要人工批准，审批记录的批准人为 `harnessix:sandbox-policy`；
  - 崩溃恢复：请求已落盘、决定未落盘时，重启后补批并完成；
  - 沙箱外命令每条弹审批，提示内容正确，拒绝后不执行。
- **非交互 `exec --approval-mode auto`**：沙箱命令执行；沙箱外命令以退出码 2 结束。
- **沙箱不可用**（ADR 0111 的 E-linux-denied 环境）：只有沙箱外命令；启动提示与修复办法正确。
- **环境变量**：沙箱外命令有代理变量、没有模型凭据；沙箱命令两者都没有。
- **兼容**：v1 记录的旧路由在重启恢复时不受影响。

## 6. 决策记录（用户 2026-11-07 拍板）

| 事项 | 决定 |
|---|---|
| 网络 | 沙箱内不能访问外网；需要联网时走逐条批准的沙箱外命令（本 ADR 第 2.2 节）；本机代理加域名白名单以后另议 |
| 沙箱内命令审批 | 自动执行，越界才问（第 2.1 节）；实现为宿主以系统身份自动批准 |
| 沙箱不可用 | 命令仍可用，但每条需批准并标注“未隔离”（第 2.3 节） |
